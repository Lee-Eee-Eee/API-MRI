# API-MRI 怎样服务课程研究

用户购买 API 时，通常能看到模型名称和价格，却很难核实每次请求经过了谁、采用了什么配置。API-MRI 围绕这个问题保存三类材料：商家作出的承诺、客户端实际收到的响应，以及继续解释差异需要的证据。

课程研究以面向中国用户的 API 聚合与中转为核心。官方 API、原厂订阅、托管和网关作为分层参照；本地或混合 Agent 是一个使用场景。我们共同讨论市场需求与价格、服务可信度、披露与责任，工具提供其中可观察的技术部分。

## 单 API 检测降低了什么成本

v0.2 要求研究者自己准备两端账户并采集。v0.3 加入公开参考包，把参考采样提前完成；v0.4 扩充兼容数据并提供按键抓取更新。使用者选择一个精确版本，再测试自己的 API。参考包保留来源、日期、题目和自测基线，候选响应可以离线重新解析。

这把一部分验证成本从个人使用者转移给参考库维护者。维护者要回答：参考来自哪个渠道、版本什么时候更新、参数是否一致、旧数据什么时候不再适用？[参考包说明](reference-packs.md)列出了内置数据的出处和未核实字段。更新功能冻结上游提交、检查兼容性并保留历史版本，让这种维护工作可检查。工具的易用性与参考的可信度需要一起研究。

## 三个可实施的研究问题

| 问题 | 可以怎样观察 | 需要补充的材料 |
| --- | --- | --- |
| 用户核验承诺需要付出多少成本？ | 记录设置步骤、实际请求量、失败和复核过程；预算确定后记录实际费用 | 套餐用途、账单及用户体验，不能用输出上限代替账单 |
| 参考包在什么条件下仍然适用？ | 校准同版本、跨时段、提示或参数变化，以及已知模型变化 | 可核实的参考渠道、明确版本和独立校准样本 |
| 技术差异怎样成为可用的投诉或审计证据？ | 将具体声明、探针响应和报告关联到同一案例 | 合同、配置变更记录、上游或运营方材料与补救安排 |

上述真实模型实验尚未开展。后续先确定合法可用的账户、预算与实验方案，再报告误报、漏检和适用条件。当前合成示例验证流程，不能替代这些测量。

v0.5 将预算作为可记录的实验条件：默认初筛最多 4 次请求，完整比较单独选择，结果保存实际发送次数、累计请求输出配额及可取得的服务自报用量。研究可以比较“花多少成本得到多少可解释信息”，也记录证据不足的比例。少问一些题是否仍能有效区分模型，需要同来源、相近替代模型与未知模型的独立测试，不能由题数直接推算。

`api-mri reference-audit --out runs/reference-audit-01` 可以离线盘点参考材料和调用计划。当前 26 份内置包各保留一份完整自测向量，其中 7 份写明参考端点；这些文件还不足以估计本工具的真实误报率或跨时段稳定性。记录更完整、允许独立复核的参考来源，应当成为后续采样与治理讨论的重点。

参考库还引出一个具体治理问题：维护者怎样说明“已有参考覆盖”和“最新模型支持”的差别？自动抓取降低了收集文件的成本，却仍需要审查参考的采集渠道、版本、配置和稳定性。更新记录可以用来比较谁负责发现失效参考、怎样更正，以及更正后历史报告怎样复核。

## 从差异到解释

知识边界指纹比较模型在一组探针上的回答模式。显著差异可能由模型变化、推理配置、系统提示、中转处理或版本更新造成。报告先定位哪些回答偏离参考，再由研究者结合服务承诺解释。

机制实验台可以帮助理解这个过程。用相同种子运行“提示改写”和“模型替换”，程序会生成相同的回答、耗时和计量。两种已知原因留下同一组外部记录，让讨论自然转向配置、日志和合同材料。混合路由、输出截断和请求不稳定则展示抽样与缺失对观察的影响。

服务研究档案把产品、日期、来源链接和模型、价格、路由、数据用途、补救声明与报告放在一起。价格需要同口径权益与账单核对；数据留存和二次利用需要运营材料。蒸馏仅作为数据二次利用的一种可能用途附带讨论。
